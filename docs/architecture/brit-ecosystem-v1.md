## 1. 플랫폼 정체성

**BRIT는 거래 상대방(Coin을 직접 사고파는 사업자)이 아니라, 사용자와 제휴 업체가 MS로 자산을 교환하는 생태계의 운영자이다.**

| 제공 | 의미 |
|------|------|
| 거래 연결 | C2C 매칭·C2B 연결/Embed |
| 자산 원장 | 사용자·(향후) 법인 MS · Lot · 불변 ledger |
| 신뢰·복구 | 잠금·멱등·대사·분쟁 |
| 정산 인프라 | 업체 전환 수수료 청구·수납 |

원칙적으로 **일반 P2P의 현금을 BRIT가 수취·보관하지 않는다.** 매칭 후 현금 이체는 당사자·금융기관 사이이다.  
현금 미보관이 **자산·중개·규제 책임을 자동 소멸시키지는 않는다** (법무 별도 검토).

P2P(현금↔MS)와 업체 포인트 전환(CHARGE/REDEEM)은 **서로 다른 업무**이며, 같은 거래 상태·완료 판정으로 섞지 않는다.

## 2. 수익 모델 (MVP 방향 · 추천)

| 업무 | BRIT 수익 |
|------|-----------|
| 사용자 ↔ 사용자 P2P | **기본 수수료 0** (MVP) |
| 업체 법인 ↔ 사용자 P2P | **기본 수수료 0** (MVP · 법인 P2P 자체는 §4 미결정) |
| CHARGE / REDEEM | **업체 계약 수수료** (주수익) |
| 정산 | 확정 수수료 청구·수납. 전환 원금과 **중복 수수료 없음** |
| 환불 | 기존 수수료 조정 여부는 계약(B7) |

C2C에 별도 수수료를 붙이는 확장은 MVP 이후. 기술 SoT는 [`merchant.md` §13](../domains/merchant.md).

## 3. 자산 장부 분리 (권장 · 문서 SoT 방향)

### 3.1 네 가지를 섞지 않는다

| 장부 | 의미 | 현재 구현 |
|------|------|-----------|
| 사용자 MS Wallet / Lot | 사용자가 보유·판매 가능한 MS | **구현됨** |
| **업체 전환 순잔액** | CHARGE(+)/REDEEM(−)로 생긴 업체↔BRIT **순포지션** | `partner_coin_wallets` (**구현됨**) |
| **업체 소유(P2P) MS** | 법인이 실제로 이전·판매할 수 있는 MS | **없음** · 법인 P2P 전 필요 (§4) |
| **수수료 채무·정산** | 완료 전환의 계약 수수료 미수 | policy/accrual/settlement 골격 |

**핵심:** CHARGE 50,000 완료로 순잔액이 +50,000 된다고 해서, 업체가 **판매 가능한 MS 50,000**을 갖게 되었다고 가정하지 않는다.  
동일 MS를 순잔액과 P2P 지갑에 **이중 소유 집계하지 않는다.**

B4 CHARGE 확정 시 순잔액 반영은 [`merchant.md` §8](../domains/merchant.md) 모델 A를 따른다. 순잔액 ≠ P2P MS 분리는 **법인 P2P·REDEEM 가치 보전**과 함께 설계한다.

### 3.2 수수료 정산 ≠ 원금·발행 책임

업체가 REDEEM으로 대량 MS를 사용자에게 지급한 뒤 P2P로 현금화되면, **수수료(예: 0.7%)만 수납**한다고 해서 원금·지급 근거가 자동 확보되지 않는다.

| 구분 | 다루는 것 |
|------|-----------|
| 수수료 정산 | 플랫폼 서비스 대가 (`partner_fee_*`) |
| 전환 순잔액·준비금·담보 | MS 발행·회수·가치 보전 관계 |
| P2P 현금 | 당사자 간 이체 (BRIT 미보관) |

둘을 한 장부로 상계하지 않는다. 발행 주체·담보는 §4.

### 3.3 REDEEM 유동성 (현행 vs 목표 논의)

| 모델 | 요지 | 상태 |
|------|------|------|
| A. 사전 확보형 | 업체가 확보·이전 가능한 MS 범위에서만 REDEEM | **추천 기본** · 미구현 |
| B. 신용 한도형 | 업체별 한도까지 순잔액 음수 허용 | **현행 SoT:** `credit_limit` ([`merchant.md` §12.4](../domains/merchant.md)) |
| C. 무제한 음수 | 한도 없이 음수 | PoC 검증용만 · **실서비스 비추천** |

현행 구현은 **B(한도형)** 이다. 사업 최종을 A 기본(+ 담보 있는 업체만 B)으로 바꿀지는 **D20**.

## 4. 미결정 — 구현 가정 금지

| ID | 항목 | 권장 논의 |
|----|------|-----------|
| **D19** | MS 발행·가치 보전 주체 | REDEEM MS = 업체 사전 확보 이전 vs BRIT 신용 기반 신규 발행 |
| **D20** | REDEEM 유동성 최종 | A 기본 + 선별 B vs 현행 `credit_limit`만 유지 |
| **D21** | 법인 P2P 1차 범위 | 법인 소유 MS 직접 주문 vs 관리자 개인 지급 후 개인 P2P만 |
| **D22** | owner / actor 분리 | 자산 소유자(법인·개인) vs 실행 계정(담당자) — `trades` user_id 중심 확장 |
| **D23** | P2P 판매·구매 분할 | 현행 split UX/API 유지 vs **분할 제외**로 SoT 개정 ([`trade.md`](../domains/trade.md)) |
| **D24** | P2P MVP 수수료 0 확정 | §2 추천을 제품 SoT로 채택할지 |
| **D13** | CHARGE/REDEEM sellable 비대칭 | [`merchant.md` §12.5](../domains/merchant.md) · MC-P3 보류. D19와 묶어서 결정 |

확정 전: 법인 P2P·별도 법인 지갑·발행 모델 코드를 **넣지 않는다.** B4(모델 A) CHARGE 오케스트레이션은 기존 merchant SoT대로 진행 가능.

## 5. 엔진 경계 (확정 방향)

1. **P2P 엔진** — 일반 사용자(및 향후 법인) 주문·매칭·입금·MS 이전. 상세: trade 도메인.  
2. **Exchange 엔진** — CHARGE/REDEEM 동일 원장·멱등·대사 원칙. B4=CHARGE, B5=REDEEM Embed.  
3. **정산 엔진** — 확정 수수료만 집계·청구. 순잔액·원금과 분리.

운영 원칙: 실패 미확정 거래 임의 종료 금지 · 완료 거래는 보상(B7) · 모든 MS 이동은 불변 원장.
